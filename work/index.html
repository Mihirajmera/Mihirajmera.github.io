WORK · 4 SHEETS

Where each tool sits in an AI system

An AI agent is an identity with tokens, a gateway that holds its model keys, a model it trusts and servers it calls. Each tool governs one part of that system and leaves evidence an auditor can re-perform. Select a label to open the tool.

  1. AI agent → MCP servers, before it runs
    Governed by agent-access-review: who owns the agent, what it can reach, and whether that's approved.
  2. AI agent → MCP servers, while it runs
    Governed by agent-flight-recorder: policy on every tool call, a human approval for risky ones, and a signed record of what it actually did.
  3. AI agent → AI gateway
    Governed by ai-gateway-audit: the gateway holds every provider key and often every prompt, so it's audited like a tier-0 system.
  4. Gateway → Model
    Governed by llm-redteam-evidence: can the model be hijacked, and is this release worse than the last?
  5. Data and egress
    Where everything meets: an agent that reads sensitive data and can send it out is flagged as an exfiltration path.

SHEET 2 · WHEN EACH TOOL RUNS IN AN AI RELEASE

  1. 1 · Approve the agent
    agent-access-review: an owner, an approved scope, and a human gate on anything that writes, sends or deletes.
  2. 2 · Configure the gateway
    ai-gateway-audit: keys out of plain text, prompts out of logs, budgets set and the image pinned by digest.
  3. 3 · Release the model
    llm-redteam-evidence: a release gate that blocks a model measurably easier to attack than the approved one.
  4. 4 · Run
    agent-flight-recorder: policy on every tool call and a signed record of each one.
  5. 5 · Audit, then recertify every 90 days
    Every stage leaves hashed evidence and OSCAL an auditor can re-perform.

SHEET 3 · HOW EVIDENCE REACHES AN AUDITOR

  1. Sources
    AI agents, the AI gateway, models and AWS accounts.
  2. Checks
    Run in CI, at runtime or on a schedule. Anything a check can't see is NOT ASSESSED, never PASS.
  3. Evidence
    SHA-256 hashed JSON and OSCAL 1.1.2 assessment results, prioritised by control-gap-analyzer.
  4. GRC platform and auditor
    A risk register with KRIs (grc-risk-dashboard) and an auditor who re-performs the checks. Expired exceptions reopen findings.

SHEET 4 · WHERE EACH TOOL SITS IN AN AWS ACCOUNT

  1. Network
    secure-vpc-architecture: segmented subnets with flow logs, as code.
  2. Identity
    iam-zero-trust-security: a least-privilege IAM baseline with automated monitoring and remediation.
  3. Detection and response
    guardduty-siem-automation: GuardDuty findings trigger automated quarantine and a findings dashboard.
  4. Evidence
    aws-compliance-as-code and itgc-evidence-automation: read-only checks and SOX ITGC evidence with hashes and OSCAL.
  5. Risk
    control-gap-analyzer and grc-risk-dashboard: control gaps scored against NIST CSF 2.0, then tracked in a risk register.

THE SAME EVIDENCE CONTRACT IN EVERY TOOL

  • Re-performableEvery result can be recomputed from its inputs, and every evidence file carries a SHA-256 hash.
  • No false passesAnything a tool can't see is reported as not assessed or needing outside evidence, never as passed.
  • Risk acceptance expiresWhere a tool accepts an exception, it needs an owner, a reason and an expiry date. Expired exceptions reopen the finding.
  • Machine-readableOSCAL assessment results for GRC platforms, and a --fail-on gate for CI.
  • ReproducibleSame input, same bytes. CI fails if the committed sample output drifts from what the code produces.
  • Secured like productionHash-pinned dependencies, SHA-pinned Actions, CodeQL, OpenSSF Scorecard, fuzzing and SLSA level 3 release provenance.
